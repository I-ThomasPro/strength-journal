# strength-journal
A simple web app for tracking and measuring training data with an emphasis on strength training.

## Backend

The API is a [FastAPI](https://fastapi.tiangolo.com/) app in `backend/`, using SQLAlchemy 2 and Alembic on PostgreSQL. All routes live under `/api`.

### Prerequisites
- [uv](https://docs.astral.sh/uv/) (installs Python 3.13 for you if needed)
- Docker, for the local Postgres database (or your own Postgres with the URLs in `backend/.env`)

### Quick start
```bash
make db-up      # start Postgres 18 (creates strength_journal and strength_journal_test)
make install    # install dependencies into backend/.venv
make migrate    # apply database migrations
make create-admin  # create your account, as an admin (asks for its details)
make dev        # run the API on http://localhost:8000
```

Then open:
- http://localhost:8000/api/health to check the API can reach the database
- http://localhost:8000/api/docs for interactive API docs

Settings come from environment variables or `backend/.env`. Copy `backend/.env.example` to get started.

### Tests and linting
```bash
make test       # pytest against strength_journal_test
make lint       # ruff lint + format check
make format     # auto-fix lint issues and format
make openapi    # export the API schema to frontend/openapi.json
```

Tests migrate the test database to the latest revision, then run each test inside a transaction that's rolled back afterwards.

After changing the API (routes, schemas or their docstrings), run `make openapi` and commit `frontend/openapi.json`; the frontend generates its API client from it. CI fails when the file doesn't match the API (`python -m app.openapi --check`).

### Migrations
```bash
cd backend
uv run alembic revision --autogenerate -m "describe the change"
uv run alembic upgrade head
```

Import new model modules in `backend/app/models/__init__.py`, which registers every model for the app and for Alembic autogenerate. CI fails if the models and migrations disagree (`alembic check`).

### Model conventions
Models live in `backend/app/models/`, one module per table, and build on `app/models/common.py`:
- `UUIDPrimaryKeyMixin`: UUID `id` generated by the app, so records can later be created offline and synced without clashes
- `TimestampMixin`: `created_at` / `updated_at`, both defaulting to now; `updated_at` is bumped on update
- `WeightUnit` (`kg` / `lb`): store it in a `WeightUnitType()` column and add `weight_unit_check("<column>")` to the table's `__table_args__`
- Other fixed sets of values (e.g. `ExerciseType`): define a `StrEnum`, store it in a `TextEnum(MyEnum)` column and add `enum_check("<column>", MyEnum)` to `__table_args__`
- Ordered children (a Routine's slots, a Workout's exercises, a workout exercise's sets, a session's set records): an integer `position` with `CHECK (position >= 0)` and `UNIQUE (parent_id, position) DEFERRABLE INITIALLY DEFERRED`, so items can be reordered within one transaction. Tests force the check with `check_deferred_constraints()` from `backend/tests/helpers.py`
- References to an exercise from another table (workout exercises, set records) use `ON DELETE NO ACTION DEFERRABLE INITIALLY DEFERRED`. An exercise in use can't be deleted, and the check waits until commit so deleting a user can cascade through both their custom exercises and their routines

Model tests use the `db_session` fixture and the factories in `backend/tests/factories.py` (e.g. `create_user(db_session, username=...)`).

### API conventions
**RESTful routes.** Resources use the Rails actions by default, with shallow nesting: collection actions under the parent when there is one, member actions flat. A resource only defines the actions it needs.

| Action | Method and path | Returns |
|---|---|---|
| index | `GET /api/[{parents}/{parent_id}/]{resources}` | `Page[XRead]`: `{"items": [...], "total": n}` |
| new | `GET /api/[{parents}/{parent_id}/]{resources}/new` | `NewForm`: `{"defaults": {...}, "options": {...}}` |
| create | `POST /api/[{parents}/{parent_id}/]{resources}` | 201 `XRead` |
| show | `GET /api/{resources}/{id}` | `XRead` |
| edit | `GET /api/{resources}/{id}/edit` | `EditForm`: `{"values": {...}, "options": {...}}` |
| update | `PATCH /api/{resources}/{id}` | `XRead` |
| destroy | `DELETE /api/{resources}/{id}` | 204 |

- **Singular resources** (e.g. `profile`, `session`, `health`) drop `index` and `{id}`, e.g. `GET /api/profile`, `PATCH /api/profile`, `DELETE /api/session`. They're listed in `SINGULAR_RESOURCES` in `app/api/restful.py` (add new ones there), and they can't be nested or be a parent
- **Parent parameters** are named after the parent, in singular: `/api/routines/{routine_id}/workouts`, `/api/workout-exercises/{workout_exercise_id}/sets`
- **Function names:** endpoint functions are named after their action, so operation IDs read `{tag}-{action}` (e.g. `exercises-create`)
- **Custom routes** are allowed when a standard action would hide what the route does. Examples: copying (`POST /api/routines/{id}/copy`), bulk reordering (`PUT .../order`), or an idempotent create-or-replace with a client-generated id (`PUT /api/set-records/{id}`)
  - Register each one in `CUSTOM_ROUTES` in `app/api/restful.py` with the reason, in the same change that adds it
  - Name its function after what it does (e.g. `copy`, which gives `routines-copy`), never after a standard action
- **Enforced:** `tests/test_restful_routes.py` checks every `/api` route against `app/api/restful.py`
  - Standard routes must fit their action's shape: lowercase nouns, hyphen-separated, nested at most one level, with singular and plural resources using their own shapes and parent parameters named after the parent
  - Any other route must be registered
  - A registered route that no longer exists also fails

**Form data.** Only add `new` or `edit` where the server supplies defaults the client can't know, e.g. a new set's targets copied from the previous set. Fixed choices such as weight units are already in the OpenAPI schema. Where they exist, they return the resource's `XUpdate` fields as `defaults` or `values`, plus `options` built with `enum_options(weight_unit=WeightUnit)`.

**Update bodies.** `PATCH` changes only the fields sent. `XUpdate` schemas extend `UpdateModel` and call `body.apply_to(item)`. A field that can't be null is declared `name: Name = omitted()`: it can be left out, but sending null is a 422. A field that can be cleared is `X | None = None`.

**Requests and errors.**
- **Transactions:** `DbSession` gives each request one transaction. It ends when the endpoint returns, before the response is sent: deferred constraints are checked, then it commits; any error rolls it back
- **Error format:** every error is `{"detail": "...", "code": "..."}` (422s add `errors` with the invalid fields). The OpenAPI schema documents 422s with this shape (`ErrorBody`). Raise `not_found()`, `read_only()`, `invalid()` or `ApiError` from `app/api/errors.py`
- **Database conflicts:** become 409s with codes from `CONSTRAINT_ERRORS` (e.g. `duplicate_name`, `exercise_in_use`), even when they fail at commit. Check constraints become 422 `invalid`

**Helpers.**
- **Pagination:** add `page: PageQuery` (`limit` 1–200, default 50; `offset`) and use `paginate()` from `app/api/pagination.py`
- **Library and owned items** (`app/api/visibility.py`):
  - `visible_to(Model, user_id)` filters a query to library items plus the user's own
  - `in_scope(Model, scope, user_id)` filters an `index` by its `scope: Scope = Scope.ALL` query parameter (`all`, `library` or `mine`)
  - `get_visible_or_404()` loads one item the user can see
  - `require_owned()` guards `edit`, `update` and `destroy`: 403 `read_only` for library items, 404 for another user's
- **Positions:** `place()` and `remove()` in `app/models/ordering.py` keep a parent's children numbered 0, 1, 2… when inserting, moving or deleting. In the API:
  - `create` appends unless the body gives a `position`; then later items shift. A `position` past the end goes last
  - `PATCH` with `position` moves one item
  - `PUT .../order` with every child's id replaces the whole order (`reorder()` in `app/api/routine_parts.py` gives a 422 unless each child is listed exactly once)
- **A routine's parts** (`app/api/routine_parts.py`): `get_routine_workout()`, `get_workout()`, `get_workout_exercise()` and `get_set()` load one only if its routine is visible; changes then need `require_owned(routine, user_id)`. `get_routine_workout_target()` and `get_usable_exercise()` give a 422 for a workout outside the routine or an exercise the user can't see
- **A routine's cycle:** workouts belong to a routine but have no position. The order they're done in is the routine's slots (`routine_workouts`, the `routine-workouts` resource), and a workout can fill several slots (e.g. A, B, A). A composite foreign key keeps each slot pointing at its own routine's workouts
- **Cycles and sessions:** a routine has one open cycle (`routine_cycles`; `open_cycle()` in `app/api/routine_parts.py`), and a workout session (`workout_sessions`, created with `PUT /api/workout-sessions/{id}` and a client-generated id) done from a slot joins it. The routine detail's `next_slot` is the slot after the user's latest completed session in the current cycle. Progression is manual: `POST /api/routines/{id}/cycles` starts the next cycle, copying each prescribed set's latest linked weight and unit (from completed sessions) into its targets
- **Set records** belong to a session (its owner and time are the record's) at a position, logged with `PUT /api/set-records/{id}`. A record done against a prescribed set links to it and copies its targets, so history keeps what was prescribed. `SetRecord.performed_at` is its session's time
- **Operation ids** must be unique (`tests/test_restful_routes.py`). A resource with indexes under two parents puts one on its own tag, as `session_set_records.py` does
- **Migration tests:** `tests/test_migrations.py` runs migrations inside a rolled-back transaction (Alembic gets the connection through `config.attributes["connection"]`), to check data moves up and down
- **Decimals:** weights are JSON strings like `"102.50"`, so they round-trip exactly. Request fields use `Weight` from `app/schemas/common.py` (0 to 9999.99, matching the columns), which keeps two decimal places, so a weight sent as `102.5` comes back as `"102.50"`
- **Nested responses:** load every level with `selectinload`/`joinedload` options (see `DETAIL_OPTIONS` in `app/api/routes/routines.py`), so a response takes the same number of queries whatever its size. `tests/test_routines.py` checks this by counting queries

API tests use the `client` fixture (or `client_for(app)` for a test-only app) and `assert_error()` from `backend/tests/helpers.py`. For endpoints that need a login, use `logged_in_client`, which is logged in as `current_user` (password `TEST_PASSWORD`) and sends the CSRF header.

### Accounts and sessions
Admins create accounts. Create the first admin from the command line:
```bash
make create-admin   # asks for the username, display name, weight unit and password (twice)
cd backend && uv run python -m app.cli create-admin --username coach --display-name Coach --password-stdin < password.txt
```
`--password-stdin` reads the password from the first line of stdin, for scripts and tests. It needs `--username` and `--display-name`, and the weight unit defaults to kg.

- **Admins:** users with `is_admin`. `POST /api/users` `{username, display_name, password, weight_unit?, is_admin?}` creates an account that can log in straight away (201). Only admins can call it: 403 `admin_only` for anyone else. Guard other admin-only endpoints with the `AdminUser` dependency (or `require_admin`) from `app/auth/sessions.py`
- **Usernames:** accounts log in with a username; there are no emails. A new username is 3 to 32 letters, digits, `.`, `_` or `-`, stored lowercased, so logging in ignores case. Accounts from before usernames (#65) kept their email as their username
- **Sign up:** `POST /api/registration` `{invite_code, username, password, display_name, weight_unit?}` (409 `duplicate_username` if taken). No screen uses it; create a single-use code with `python -m app.cli create-invite [--days 7]`
- **Log in:** `POST /api/session` `{username, password}`; check who's logged in with `GET /api/session`; log out with `DELETE /api/session`
- **Profile:** `GET /api/profile`; `PATCH /api/profile` `{display_name?, weight_unit?}`
- **Password:** `PATCH /api/password` `{current_password, new_password}` (401 `invalid_credentials` if the current one is wrong). It logs out every other device
- **Devices:** `GET /api/sessions` lists the user's logins (`current` marks this one); `DELETE /api/sessions/{id}` logs one out
- **Passwords:** hashed with Argon2 (`pwdlib`), at least 10 characters
- **Sessions:**
  - Stored in Postgres (`user_sessions`), with only a SHA-256 of the cookie token
  - The cookie is HttpOnly, SameSite=Lax and Secure (unless `COOKIE_SECURE=false`)
  - Sessions last `SESSION_DAYS` (30), and the expiry moves forward on use, at most hourly
- **CSRF:** the frontend sends the `csrf_token` from `GET /api/session` as an `X-CSRF-Token` header on every POST/PUT/PATCH/DELETE. Separately, unsafe requests are rejected if their `Origin` isn't `ALLOWED_ORIGIN`, or if their body isn't JSON
- **Code:** endpoints get the logged-in user with the `CurrentUser` dependency from `app/auth/sessions.py` (401 `not_authenticated` without a session)

## Frontend

The web app is a React + TypeScript single-page app in `frontend/`, built with Vite, styled with Tailwind CSS and shadcn/ui, and routed with React Router. It's served from the same origin as the API, so in development Vite proxies `/api` to it.

### Prerequisites
- Node 22.22 or later (`frontend/.nvmrc`)
- pnpm 10: `corepack enable` installs the version pinned in `frontend/package.json` (run pnpm commands inside `frontend/`, as the Makefile does, so Corepack finds that pin)
  - With asdf, run `asdf reshim nodejs` after `corepack enable`, so the `pnpm` command appears
  - If Corepack fails with "Cannot find matching keyid", it's too old for npm's current signing keys: run `npm install -g corepack@latest`, or use a recent Node 22

### Quick start
With the API running (`make dev`, above), in another terminal:
```bash
make fe-install # install dependencies into frontend/node_modules
make fe-dev     # run the app on http://localhost:5173
```

Vite forwards `/api` requests to `http://localhost:8000` (set `API_URL` to use another address), so the browser sees one origin and the session cookie works as in production. The port is fixed at 5173 because the API only accepts writes from its `ALLOWED_ORIGIN`, `http://localhost:5173` by default. For plain-HTTP development, set `COOKIE_SECURE=false` in `backend/.env`, as `.env.example` does.

### Tests and linting
```bash
make fe-test    # Vitest + Testing Library
make fe-lint    # ESLint, Prettier check and typecheck
make fe-format  # fix lint issues and format
make fe-build   # typecheck and build into frontend/dist
make fe-e2e     # Playwright end-to-end tests against the real API
```

### End-to-end tests
Playwright (`frontend/e2e/`, `frontend/playwright.config.ts`) drives the real app and API in Chromium at phone size.
- **Setup:** install its browser once (from `frontend/`): `pnpm exec playwright install chromium`. Postgres must be running (`make db-up`)
- **Running:** `make fe-e2e`. It starts its own API on port 8001 and app on port 5174, so it can run while `make dev` and `make fe-dev` use 8000 and 5173
  - The tests use their own database, `strength_journal_e2e`. They commit data, while the pytest database relies on rolling back
  - The global setup creates that database if it's missing and migrates it
  - Set `E2E_DATABASE_URL` if your Postgres isn't the one `make db-up` starts
- **Writing tests:** import `test` and `expect` from `e2e/fixtures.ts`
  - The `admin` fixture is a fresh admin for each test, made with `python -m app.cli create-admin --password-stdin`
  - `logIn(page, account)` logs in through the login page
  - `uniqueUsername()` keeps tests that run at the same time apart
  - `addExercise(page, name)` adds one of the logged-in user's exercises through the API
- **Debugging:** traces are off; re-run a failing test with `pnpm e2e --trace on` (from `frontend/`), then `pnpm exec playwright show-trace`
- **CI:** the End-to-end workflow (`.github/workflows/e2e.yml`) runs `make fe-e2e` on every change to `frontend/` or `backend/`, against a Postgres service. The browser is cached by Playwright version. When a test fails, the run uploads the HTML report, with a screenshot of each failing test, as the `playwright-report` artifact
- **Without Playwright's download:** set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` to a Chromium binary you already have, instead of installing one

### API client
The app talks to the API through TanStack Query hooks that [Orval](https://orval.dev/) generates from `frontend/openapi.json` (`orval.config.ts`):
- **Generated, not committed:** `pnpm generate` writes them to `src/api/generated/`, and `dev`, `build`, `typecheck`, `lint` and `test` run it first. After `make openapi`, restart `make fe-dev` or run `pnpm generate` to pick up API changes
- **Names:** one module per tag, with hooks named after operation ids: `useExercisesIndex()` from `@/api/generated/exercises` for `exercises-index`, `useSessionCreate()` for `session-create`. Request and response types are in `@/api/generated/model`
- **Requests:** every request goes through `apiFetch` in `src/api/client.ts`. It sends the session cookie and JSON, and adds the `X-CSRF-Token` header to writes. The token is set with `setCsrfToken()` and read as each request is sent
- **Errors:** a failed request throws one of two errors:
  - `ApiError`, with `status`, `code` (e.g. `duplicate_name`) and `detail`. Its `errors` list holds a 422's invalid fields as `{field, message, type}`, with dotted paths like `sets.0.reps`. `isApiError(error, 'not_found')` checks for one code
  - `NetworkError`, when no response arrived (e.g. offline)
- **Retries and caching** (`src/api/query-client.ts`): queries retry network errors and 5xx responses up to three times but never a 4xx, and data stays fresh for 30 seconds. The TanStack Query devtools open from the top-right button in development
- **Weights** stay decimal strings, as the API sends them (`"102.50"`). `formatWeight()` and `parseWeight()` in `src/lib/weight.ts` convert them for display and from input
- **Tests:** MSW (`src/test/server.ts`) stands in for the API. A test adds the responses it needs with `server.use(...)`, and any request without a handler fails. `renderWithQueryClient()` in `src/test/render.tsx` renders a component with a fresh query client that doesn't retry

### Conventions
- **Imports:** `@/` is `frontend/src/`, e.g. `import { Button } from '@/components/ui/button'`
- **UI components:** shadcn/ui components are copied into `src/components/ui/`, and the project owns and edits them. Add one from `frontend/` with `pnpm dlx shadcn@latest add <component>`. The theme's colors and radius are CSS variables in `src/index.css`
- **Classes:** combine conditional Tailwind classes with `cn()` from `@/lib/utils`. Prettier sorts class names
- **Routes** (`src/routes.tsx`):
  - Signed-out pages go under `PublicLayout` (a centered card), and signed-in ones under `AppLayout` (header and tab bar). The tab bar's tabs and icons are in `src/navigation.ts`
  - Each route gives its title with `handle: titled('…')`. The layout's header shows it, and the browser tab gets "Train · Strength Journal" (`usePageTitle` in `src/lib/page-title.ts`)
  - A page that fails to render shows `RouteErrorPage`, with a "Reload" button, inside the layout
  - A page outside the tab bar belongs to a tab through that tab's `sections` (`src/navigation.ts`), and the tab stays highlighted there. `/exercises` is a section of Routines
- **Session** (`src/auth/`):
  - `SessionGate`, the root route, loads `GET /api/session` before any page shows, with a splash meanwhile, and keeps the CSRF token in step with it
  - Components read the user with `useSession()` (`{status, user}`). Being logged out is `status: 'logged-out'`, not an error
  - The session lives in the query cache under `sessionQueryKey`: logging in stores the response there with `setQueryData`
  - **Logging out:** `useLogout()` (`src/auth/logout.ts`) sends `DELETE /api/session`. It then sets the session to `null`, which clears the CSRF token and sends the guard to `/login`, and removes every other cached query, so nothing shows after the next login. A session that had already expired is forgotten too; any other failure leaves the user logged in, with `logoutErrorMessage()` saying why
  - **Offline:** login and logout use `networkMode: 'always'`. They try even when the browser says it's offline, so the user hears at once that it didn't work, instead of the request waiting for the network (TanStack's default, which offline workout logging will rely on)
  - **Guards** (`src/auth/guards.tsx`):
    - `RequireLogin` wraps the signed-in pages and sends a logged-out user to `/login?next=<where they were>`
    - `RedirectIfLoggedIn` wraps the signed-out pages and sends a logged-in user on to `?next=` or Train. That's also how the login page moves on once it stores the session. `safeNext()` keeps the redirect on this site
  - **Expired sessions:** a 401 `not_authenticated` on any query or mutation sets the session to `null` (`endSessionIfExpired` in `src/api/query-client.ts`), so the guard sends the user to log in and back. A 401 `invalid_credentials` (a wrong password in a form) doesn't
- **Admin-only pages:** a tab with `adminOnly: true` (`src/navigation.ts`) shows only to admins, and its page sits inside `RequireAdmin`, which sends anyone else to the not-found page
- **Forms:** react-hook-form, laid out with `FormField` and `FormMessage` (`src/components/form-field.tsx`). The helpers are in `src/lib/forms.ts`:
  - Give each input `{...fieldAria(id, {hint, error})}`
  - On a failed request, call `showRequestError(error, setError, FIELDS, {code: field})`. It puts a 422's errors on their fields, and mapped codes such as `duplicate_username` on theirs. Everything else goes at form level, with a network message when offline
  - Mutations the user waits on use `networkMode: 'always'`, so offline they fail at once
  - A new password's minimum length and its hint are `MIN_PASSWORD_LENGTH` and `PASSWORD_HINT` in `src/auth/password.ts`, which matches the API's minimum
- **Lists:**
  - Filters go in the address with `useSearchParams` (the Exercises list's `?scope=mine&q=squat`), replacing the history entry, so a reload or coming back shows the same list
  - A search box updates the address once the typing pauses: `useDebouncedValue()` (`src/lib/debounce.ts`)
  - A row that opens a detail page passes the list's address in the link's `state`, and the detail's back link returns there: `FromList` and `listToReturnTo()` (`src/exercises/list-address.ts`)
  - Paging is "Load more" over an infinite query, e.g. `useExercisePages(scope, q)` (`src/exercises/exercise-pages.ts`). Its key starts like the generated hook's, so invalidating `getExercisesIndexQueryKey()` after a write reloads every search and page, as `NewExerciseForm` does
- **Offline:** a screen that needs a connection shows `<OfflineNotice>` (`src/components/offline-notice.tsx`), which appears only while the browser is offline. `useOnline()` (`src/lib/online.ts`) gives the same state, e.g. to disable a button
- **Tests that render pages:** use `renderApp(path, ...handlers)` from `src/test/render.tsx`. It renders the real routes with the app's query client (without retries), answering `GET /api/session` as logged out unless a handler such as `loggedInAs(user)` (`src/test/session.ts`) comes first. Signed-in pages need `loggedInAs()`. For screens that list or show exercises, `answerExercises(all)` (`src/test/exercises.ts`) answers `GET /api/exercises` by scope, name and page, and `GET /api/exercises/:id`
- **Tests:** next to the code as `*.test.tsx`. Query by role and accessible name, as a user would find things. `src/test/setup.ts` adds the jest-dom matchers (`toBeInTheDocument()` and others)
- **Linting:** ESLint uses type information (e.g. it flags a promise that's never awaited or handled), React's hooks rules and jsx-a11y's accessibility rules
